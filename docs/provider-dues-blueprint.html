01

Executive summary

Network Services collects annual dues from providers in the Texas CIN. Today invoices are produced outside Salesforce, providers can only pay by check, payment status is invisible in the CRM — and in 2024, 17% ($172k) of dues went uncollected.

This design replaces that with an automated pipeline: a roster file lands, a daily job resolves and deduplicates it, provider charges roll up into one obligation per account, a Pay Now link is generated, notices go out on the approved calendar, and payment settles straight back onto the obligation — with a nightly reconciliation that turns "usually right" into "provably correct".

Two principles govern every decision that follows.

Principle 1 — the obligation is the source of truth

The dues obligation record states what an account owes, whether it is paid, and what was sent to them. Roster files and provider assessments are inputs that can be replayed or purged; the obligation is not.

Principle 2 — configuration over code

Anything that varies by market, year, price, cadence or notification rule lives in Custom Metadata — not Apex, not Flow decision elements. Onboarding market #2 must require zero lines of new code.

The three questions the team asked up front

Can Salesforce email ~10K accounts today?

Yes — throttled

The org-wide cap is 5,000 external recipients per day, shared with every other feature. Send in a throttled window, never a single blast.

Can Salesforce email 100K accounts later?

No

100,000 ÷ 5,000/day = 20 days for one notice event. No configuration, limit-increase or email-alert trick changes this.

So what do we build now?

A channel interface

The dispatcher writes to an interface; a metadata value picks the implementation. Salesforce email for MVP, Marketing Cloud Next or an ESP later — same code.

02

The journey, end to end

Stage 1 — Load

The roster arrives

The upstream team bulk-loads NPI, TIN, amount and dues year. Rows may repeat; a corrected file may follow an hour later. Everything is stored exactly as delivered — nothing is rejected at load time.

Stage 2 — Bill

One obligation per account

Each row is matched to a provider and a billing account, duplicates collapse on NPI + TIN, and the provider charges add up to a single amount owed. An account with 12 providers gets one bill, not twelve.

Stage 3 — Notify

Link and reminders

A secure Pay Now link is generated and emailed to the billing contact on the approved calendar. Every send re-checks that the account is still unpaid before it goes.

Stage 4 — Collect

Paid, closed, reconciled

The provider pays on the hosted page. The obligation is marked Paid, remaining reminders are cancelled, a receipt goes out, and anything unpaid after the final notice becomes a termination review task.

The case that matters

If one repeated row carried a different amount — $215 against $250 — the pipeline does not guess. It raises an exception, excludes that provider from the obligation, and puts it in the exception queue for business correction. No obligation is ever published from a file that does not balance.

The four keys that make the pipeline safe

Every stage is idempotent because of a deterministic key. Re-running any job produces the same result — it never double-charges, double-links or double-emails.

Why RowKey is deliberately not unique

The roster is ingested as delivered. A unique constraint at the staging layer would make the upstream bulk load fail on duplicate rows — the exact failure we must avoid, because a failed load is worse than a duplicate row. Deduplication happens on the way into assessments, where we control the transaction. This is the direct answer to "we can't use NPI or TIN as unique — we need to ingest whatever we get, then calculate."

The operational promise

Turning notifications off in production is edit one checkbox → save. No deployment, no code review, no release window. Every job reads the flags at the start of every run, and the dispatcher re-reads them immediately before each send. Custom Metadata records are editable directly in production and still version-controlled as metadata — which is why they, and not constants or Custom Settings, are the right home for these switches. Grant edit rights through a dedicated permission set; changes land in the Setup Audit Trail.

Splitting config from data matters here: market rules live in metadata (deployable, rarely changed), while the cycle — this year's dues year, invoice date and due date — is a record the business edits without involving a release.

Important nuance on "don't run if there is no file"

The roster stages (1–5) skip when no new file arrived — no batch is enqueued at all, so no async slots are consumed. 07

Roster ingestion and picking the latest file

The load itself must not be slowed down

  • Dues_Roster_Row__c has no Apex trigger, no flow, no roll-up summary, no querying validation rule. Load throughput is protected absolutely; all processing is deferred to the scheduled batch.
  • The only exception is an optional, metadata-bypassable after-insert trigger that upserts the file header — one query and one upsert per 200 rows, never per row. If the upstream team creates the header themselves, even that is removed.
  • Fields are wide text at ingest (NPI_Raw__c, TIN_Raw__c, Amount_Raw__c) so a malformed value stores rather than rejects. It becomes a reportable exception in stage 1, not a load failure.

Choosing the latest file

Why the quiet period exists

A 200K-row Bulk API load takes minutes. If the daily job fires mid-load, "the latest file" is a partial file and every obligation it produces is understated. An explicit completion signal (preferred) and a configurable quiet period (fallback) both guard against it. Both are metadata-driven.

A corrected file arriving after processing is handled as a re-run against the same cycle: assessments are upserted by key, providers no longer present are marked Removed, and the obligation is recomputed — unless it is frozen, in which case it goes to the adjustment queue rather than silently changing a bill someone has already received.

Verify V-05 — ask the upstream team for a file id

Without a file or batch identifier, "latest file" degrades to grouping by created-date bucket, which merges two loads in the same window and splits a slow one. One text column removes the risk entirely.

Identity resolution — never row by row

The batch collects the distinct NPIs and TINs in its chunk and issues a small fixed number of bulk queries. Ambiguity is never resolved by guessing: more than one active account for a TIN raises AMBIGUOUS_ACCOUNT with all candidates listed, because a wrong bill-to means a wrong invoice to a real customer.

// One query per identifier type per chunk — not per row
Map<String, Id> providerByNpi = new Map<String, Id>();
for (HealthcareProviderNpi n : [
        SELECT Id, NpiNumber, HealthcareProviderId
        FROM HealthcareProviderNpi
        WHERE NpiNumber IN :npiSet
          AND (EffectiveToDate = NULL OR EffectiveToDate >= :cycleStart)]) {
    providerByNpi.put(n.NpiNumber, n.HealthcareProviderId);
}

NPI is read from the structured Health Cloud identifier record. A display name is never parsed to derive an NPI — pipe-delimited names are not a data contract.

08

Deduplication and the accuracy invariants

This is the accuracy-critical stage — the one the business will judge the system on.

AssessmentKey = CycleId + '|' + MarketCode + '|' + normalize(NPI) + '|' + normalize(TIN)

A provider practising under two TINs is two legitimate assessments on two obligations. A provider repeated under the same TIN is one.

Strategy (metadata-selected)BehaviourUse
COLLAPSE_IDENTICAL_ELSE_EXCEPTION (default)Identical amounts collapse silently; differing amounts raise DUPLICATE_AMOUNT_CONFLICTDues — never invent a number
LAST_ROW_WINSHighest source row number winsFeeds where later rows are corrections
MAX_AMOUNTHighest amount winsConservative billing
SUM_LINESRows are separate line items and are summedMulti-line fees in a future market
INV-1 — the total comes from assessments, never from raw rows

Because Assessment_Key__c is unique-enforced at the database level, a provider cannot be counted twice in a cycle for a TIN — regardless of how many times the file repeats them, how many times the job runs, or whether two jobs overlap. The database, not the code, is the guarantee.

INV-2 — round at the line, sum the rounded values

Amounts are rounded to two decimals at the assessment level and the obligation is the sum of already-rounded values. Rounding only at the total would let the invoice disagree with its attached roster by cents.

INV-3 — every obligation carries a calculation hash

A hash of the ordered contributing (key, amount) pairs. Reconciliation recomputes it nightly; a mismatch means data changed behind the pipeline's back and raises an exception.

INV-4 — nothing publishes from an unbalanced file

Valid + exception must equal the control total, and every exception must have an ops disposition, before a single notice goes out.

DML is deliberately partial-success — Database.upsert(records, key, false) — so one malformed row never fails the other 1,999 in its chunk. Each failure is captured with its source row reference.

09

Roll-up to the obligation

Why not a roll-up summary field

Master-detail plus a roll-up summary is the free answer, and it is the wrong one for a billing number.

ConcernRoll-up summaryDeterministic recompute (chosen)
Freeze after publicationImpossible — a late child edit silently changes an invoiced amountFreeze flag blocks recompute; changes route to adjustments
AuditabilityNo record of when or why the number changedCalculated-at timestamp, calculation hash, run log
RestartabilityOpaqueRe-run any time, same result
Insert orderingParent must exist before childrenParent upserted by key in the same stage
Object model costConsumes a master-detail slot, reparenting limitsPlain lookup

For a number people will pay and dispute, an amount that can change silently is a defect. Recompute wins.

Chunk boundaries are handled, not hoped for

Ordering the batch by account keeps an account's assessments contiguous, but a chunk boundary can still split one account across two chunks. Run-scoped additive accumulation handles it:

for each (account, currency) group in this chunk:
    obligation = upsert by ObligationKey
    if (obligation.Rollup_Run_Id__c != currentRunId):   // first touch this run
        obligation.Amount_Due__c      = chunkSum        // reset
        obligation.Provider_Count__c  = chunkCount
        obligation.Rollup_Run_Id__c   = currentRunId
    else:                                               // continuation chunk
        obligation.Amount_Due__c     += chunkSum        // accumulate
        obligation.Provider_Count__c += chunkCount

Batch chunks for one job execute serially, so accumulation is deterministic, and the run-id reset makes the whole job idempotent — re-running produces the same totals, never doubled ones. The final chunk stamps the timestamp and calculation hash.

Batch Apex constraint worth knowing

start() cannot return a GROUP BY aggregate as a QueryLocator. Hence the row-level locator with in-chunk aggregation above. Beyond roughly 100K accounts, switch to two-phase: write per-run, per-account partials, then sum partials into obligations. Same keys, same invariants, no ceiling — a planned step rather than a surprise.

Single-provider accounts need no separate code path — they are simply an obligation with a provider count of 1. Whether the notice carries a roster attachment is a metadata threshold.

The approval and freeze gate

No obligation publishes until the file balances, every exception has a disposition, business approval is recorded on the cycle, and contributing assessments are locked. On approval the amount is frozen. This gate is what makes the number trustworthy — after it, nothing changes the amount except an explicit, audited adjustment. Auto-approval is available per market for markets that do not want a manual gate.

Payment links at 10K+ scale

Salesforce Payments provides a Generate Payment Link flow action, normally used from a record-triggered or screen flow. At 10,000 obligations that pattern fails on three counts: one flow interview per record, one gateway callout per record with no batching or throttle, and no retry or dead-letter path when the provider rate-limits or times out.

Verify V-01 — and why it does not block us

The exact action API name, its parameter contract and whether it accepts a list are org- and release-specific. IPaymentLinkProvider exists precisely so that uncertainty is contained in one class. If the action proves unsuitable, we swap the implementation for a supported REST call or a gateway adapter — the batch, the obligation model, the notification engine and every test stay untouched.

Governor budget and throughput

Throughput: 10,000 obligations ÷ scope 10 = 1,000 chunks × ~3 s ≈ 50 minutes, run overnight, days ahead of the first notice. Scope is metadata-tunable, so it is dialled in during performance testing rather than redeployed.

No duplicate links, ever

The request id is stamped before the callout. If the transaction dies after the gateway created the link but before Salesforce committed, nightly reconciliation finds the orphan and repairs the obligation instead of generating a second link. Only one link may be active per obligation; regeneration after an approved adjustment deactivates the previous one first, so an old email never points at a stale amount.

Decision D-04 — "one-time-use" needs a business ruling

The PRD says "a unique, one-time-use payment URL for each invoice", but the same link is emailed in up to five notices. Interpretation adopted: the link is unique per obligation per cycle, with a locked predefined amount, deactivated on successful payment — one-time-payment, not one-time-open. A fresh nonce per email would multiply link volume fivefold, break the reminder flow and confuse a payer holding an earlier email.

Checks still work. A "Record Offline Payment" action writes method, reference, date and amount through the same settlement service used by card and ACH — so a check payment also cancels remaining reminders, sends a receipt and closes assessments. One settlement path, not two.

Decision D-03 — a discrepancy to close

The notification lifecycle diagram shows T−30 / T−15 / T−7 with a 1 January due date; PRD §4.3 specifies the calendar above with a 30 January due date. The PRD dates are implemented and the diagram should be updated. Because both are pure configuration, correcting it later costs one metadata edit — but templates and business communications should be built against the right dates from day one.

Materialise, then dispatch

Planned notices are created for the whole cycle the moment an obligation is approved, then a daily dispatcher claims the ones that are due. Separating the two means operations can see exactly what an account will receive and when, notices can be cancelled en masse on payment before they are ever sent, and the send step is a small, restartable, throttleable job.

Send-time guards, all re-checked immediately before sending

  1. Master kill switch off → abort the run
  2. Notifications enabled, and this notice type active → else Suppressed
  3. Obligation still unpaid → else Suppressed. This is the PRD's "stop on payment", enforced twice: at settlement and at send
  4. Lifecycle is Approved or Published, not Cancelled
  5. Active, unexpired payment link present
  6. Recipient resolved and not bounce-flagged
  7. Daily send cap not exhausted → else deferred to tomorrow, never silently dropped

MessageKey uniqueness means a double-run of the dispatcher cannot produce a second email. A schedule version increments if the business changes the calendar mid-cycle, which intentionally allows a corrected notice without breaking that guarantee.

Recipient resolution ladder (metadata-ordered): designated billing contact → account primary contact → account billing email field → NO_RECIPIENT exception. Never a guessed address. The resolved address is snapshotted on the communication row, so a year later the record still shows exactly where the notice went even if the contact has since changed.

Payment settlement

The requirement — "when the Payment Intent record is updated, tag it to the dues obligation, and we can do that with Flow" — is the primary path. Two caveats drive the fallbacks:

Verify V-03

Confirm that PaymentIntent supports record-triggered flows or Apex triggers in this org and release. Some managed and standard payment objects do not.

Even where it does, event-driven settlement can miss — a flow error, a mixed-DML failure, a deployment window. The 15-minute correlation batch is always on. It is the difference between "payment status is usually right" and the PRD's key result of 100% data accuracy.

Concurrency: settlement re-queries the obligation FOR UPDATE inside the transaction. Two concurrent events serialise; the second sees Paid and no-ops. With receipt MessageKey uniqueness, a duplicate event cannot produce a duplicate state transition or a duplicate receipt.

Partial payment never auto-marks Paid — status becomes Partially Paid, finance gets an exception, and reminders continue by default (switchable per market).

Retention and purge

Conflict to resolve — Decision D-02

The requirement is to delete roster and assessment records after one year. But PRD §4.2 requires payment and communication history for five years, and group invoices are issued "with an attached roster". If provider-level assessments are deleted at twelve months, the org can no longer reproduce which providers a three-year-old invoice covered — exactly the evidence needed in a billing dispute or audit.

Resolution: archive, then purge

1
QualifyCycle closed and older than the retention window
2
ArchiveSerialise contributing assessments to a compressed file attached to the obligation
3
StampArchived-on date and archive checksum on the obligation
4
PurgeBatch-delete assessments, then roster rows — keep the file header
5
RetainObligations and communications kept 5 years+

Purge guards, all mandatory

  • Purge flag must be true — default false. A destructive job is never on by default.
  • Cycle closed and due date older than the retention window.
  • Never delete anything attached to an obligation that is unpaid, partially paid or in dispute.
  • Dry-run mode reports the counts it would delete, for one full cycle of review before the first live purge.
  • Every run writes a log with counts and archive references.

At ~200K rows a year, roster staging is material against data storage — which is exactly why the one-year purge is right. The archives live in file storage, far cheaper, and preserve the audit trail.

Bulk standards and the limit budget

  1. No SOQL, DML or callout inside any loop. Reviewed at PR time, enforced by static analysis in CI.
  2. Every service method takes a collection. No single-record public entry points except a thin wrapper for quick actions that delegates to the bulk method.
  3. One trigger per object, handler pattern, with a metadata bypass so data loads and migrations disable triggers without a deployment.
  4. The staging object stays trigger-free.
  5. Selective queries only — filter on External Ids, lookups and created dates; avoid negations, leading wildcards and formula-field filters on large objects.
  6. Scopes are configuration, not constants: 2,000 for DML stages, 200 for resolution-heavy stages, 10–20 for callout stages.
  7. Stateful only for counters — never for record collections.
  8. Bulk API 2.0 for the inbound load; never row-by-row synchronous insert.
  9. Volume tests at 10× expected: 200 and 2,000-record chunks in unit tests, a 100K-row load in full sandbox before go-live.

Security and compliance

  • PCI: no card number, CVV, expiry or bank account in any custom field, debug log or exception message. Settlement code allow-lists the fields it copies — it never serialises a whole payment record into a log.
  • The payment link URL is a bearer secret. Field-level security restricts it to the dues operations permission set, and it is excluded from broadly shared report types and the guest profile.
  • Guest access: the Pay Now site is the managed data channel. Custom dues objects are not exposed to the guest user.
  • Least privilege: four permission sets — Operations, Finance, Admin, Integration. No profile-level grants.
  • Named credentials for any external channel; no endpoints or keys in code or metadata text.
  • Audit: field history on amount, status and payment fields; Setup Audit Trail on metadata flag changes.

Three consequences that shape the build

  1. The 5,000 is the org's budget, not ours. A dues blast consuming 4,800 recipients can break unrelated business processes for the rest of that GMT day.
  2. Over-cap sends fail rather than queue. There is no built-in retry — without throttling we lose notices and never learn which ones.
  3. Email alerts are not a way around it in a modern org; the same cap covers them. Neither is Email Relay, which changes the route, not the allocation.

What we build in MVP — inside the time constraint

  1. Throttle by configuration. Daily cap, recommended start 1,500/day, leaving the rest of the org's budget intact.
  2. Spread the initial notice over a configurable window (e.g. 3 days). Oldest scheduled notices go first; the remainder rolls to tomorrow as Deferred — visible, never dropped.
  3. Check remaining capacity before sending. Messaging.reserveSingleEmailCapacity() reserves headroom and fails fast; a lightweight read of the org limits endpoint gives the dispatcher an accurate figure at run start.
  4. Never exceed 10 send invocations per transaction; batch recipients within each.
  5. Send off-peak (early GMT) so a partial failure leaves the same day to recover.
  6. Bounce handling: enable Bounce Management, flag bounced contacts nightly, suppress further sends to that address, raise the manual follow-up task the PRD requires.

Where the boundary honestly sits

A genuinely new concept still needs code — instalment plans, proration arithmetic, a new payment channel, or a billing level that is neither account nor provider. The gap report needs a real design

"Providers in Health Cloud with no dues assessment for the current cycle" is a does-not-exist query, which Salesforce reports handle poorly at scale. Recommendation: a nightly detection batch writes gap records, and the report runs on that object. This also gives a working queue with assignment and resolution state — which a report of absences cannot — and it is what actually triggers the manual dues-assignment task the PRD describes.

Dashboard: total assessed, total collected, outstanding balance, collection rate, unpaid providers, overdue accounts, records needing manual intervention, status by account and by NPI, aging by days overdue — plus operational tiles: exception queue depth, link success rate, notices sent/failed/deferred today, unreconciled payments.
